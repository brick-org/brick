This module targets the server-side behavior of Better Auth **v1.7.5**, pinned
at `vendor/better-auth` commit `5468e6bfcdff799848537cf5ad06ebab15aad9dd`.
It is a standalone Go module and does not depend on the Brick runtime.

## Compatibility status

> **V1 scope is core-only: email/password + session (see [`SCOPE.md`](./SCOPE.md)).**
> Plugin, OAuth-provider, and social-provider `Done` claims elsewhere in this
> file are superseded — those directories do not exist in this tree.

The Go module targets the v1-declared scope of Better Auth v1.7.5
server-side behavior: the 23 core routes, cookies, crypto, DB/schema/adapter,
and public types listed in `SCOPE.md`. Within that scope, every file below
has reached Done, verified against the pinned source and tests.

Status terms used below:

- **Done**: no known v1.7.5 server-side parity task remains in that file's
  declared scope; intentional Go/platform differences are called out as
  exclusions.
- **Different**: intentionally or historically uses an incompatible contract.
- **Go-only**: infrastructure needed by this port, with no direct TS file.

## Endpoint coverage

### Core

All 23 v1 core route paths have Go equivalents (see [`SCOPE.md`](./SCOPE.md)).
Excluded from v1 by decision (not missing): `/sign-in/social`,
`/callback/{provider}`, `/account-info`, `/link-social`, `/unlink-account`,
`/get-access-token`, `/refresh-token`.

Important remaining contract differences are narrow and listed as intentional
exclusions below:

- `/verify-email` supports the upstream GET/query/redirect contract and keeps
  a Go POST alias. Routes issue HS256 email JWTs by default
  (`CreateEmailVerificationToken`), with legacy HMAC readable as a bounded
  migration bridge (`VerifyEmailTokenWithFallback`).
- Password reset uses atomically consumed `reset-password:*` rows and supports
  `redirectTo`; legacy signed tokens remain readable as a migration bridge.
- Session `jwt`/`jwe` cookie-cache strategies are wired
  (`CreateSessionCacheJWT`/`CreateSessionCacheJWE` with claim/version/key
  binding, rotation, and fail-closed unknown-key handling); the custom
  JWKS-signer path is owned by the JWT plugin. Secondary-storage
  sessions/verifications persist with a flag matrix; flags without a backend
  still error at startup.
- Additional-field transforms/validators, request-aware callbacks,
  per-request dynamic base-URL rewriting, and middleware context/error
  behavior are wired; the narrow remainders (unknown-key sign-up bodies,
  empty-query GET, `WWW-Authenticate` headers) are intentional exclusions.
- OAuth social callback/state/nonce/issuer and client-submitted `id_token`
  flows are wired, including trusted `serverContext` production (client input
  can never inject it) and request-aware custom verifiers.

## Intentional exclusions

- `src/client/`: browser/client state belongs in generated clients.
- `src/integrations/`: JavaScript-framework adapters do not map to the Go
  server library; Go auth mounts through a Huma adapter.
- TypeScript-only inference and Zod conversion helpers are replaced by Go
  types and Huma schemas rather than copied mechanically.
- Plugins without a Go implementation are not represented by placeholders.

### Decision registry (AUTH-R5-03, pinned by `decisions_test.go`)

- `Options.DB` naming (D01): upstream `BetterAuthOptions.database`
  (`packages/core/src/types/init-options.ts:621`) is `DB` in Go
  (`types/auth.go:1207`). Renaming is source-incompatible churn with no
  behavioral gain. Never add a `Database` alias. Stable, no removal policy.
- Random-ID alphabet (D02): upstream `generateId` is alphanumeric
  (`packages/core/src/utils/id.ts:3`); Go `GenerateID` uses the
  `generateRandomString` `-_` set (`crypto/random.go:13`). Changing the
  alphabet is observable (stored IDs/URLs/tokens). Removal requires a
  major-version writer cutover with dual-read, migration reads, and TS
  fixtures only.
- PKCE plain mode is not implemented (D03: `crypto/pkce.go`; upstream emits
  S256 only, `packages/core/src/oauth2/create-authorization-url.ts:89-91`).
  Accepting plain would let a network observer replay the challenge as the
  verifier. No removal policy.
- IDNA/punycode (D04): unicode hosts compare lowercased-only; `xn--` and
  unicode spellings never match (fail-closed). A faithful equivalent needs
  `golang.org/x/net/idna`, deliberately not in `auth/go.mod`. Revisit only
  with TS↔Go fixtures proving both spellings.
- Non-transactional after-hook errors propagate to the caller (D05 aligned
  to upstream throw in AUTH-S6-01: `hooked_adapter.go:153`; write stays
  committed, row returned alongside the error, logger additionally reports).
  Upstream pin: `packages/core/src/context/transaction.ts:170`.
- OAuth state writes keep Go spellings (D06: `errorCallbackURL`,
  `newUserCallbackURL`, flat `linkUserId`/`linkEmail`) while reads accept
  upstream spellings (`errorURL`/`newUserURL`/`link:{email,userId}`,
  `packages/better-auth/src/state.ts:12-16`). Writer cutover to TS spellings
  requires TS fixtures (Wave 7).
- MSSQL `OUTPUT inserted` is unused (D07): MySQL/MSSQL use the cascading
  re-read fallback (`adapters/bun/bun.go:63`); upstream kysely uses
  `top(1)`+`OUTPUT` on mssql. Removal only if live MSSQL runs prove the
  re-read wrong (AUTH-D6-01 still owes live MySQL/MSSQL wire runs).
- Unregistered OAuth audiences keep the legacy allow-list (D08:
  `ValidAudiences`/BaseURL without a stored `oauthResource` row) unless
  `StrictResourceValidation` is set, which rejects with `invalid_target`
  (upstream `authorize.ts:647`). Default flip is major-version-only with a
  migration note.
- Admin factory stays permissive for custom `adminRoles` outside the roles
  map (D09: `admin.go:158`); upstream throws at factory (`admin.ts:54-67`).
  Removal: add an opt-in strict flag, never throw by default.
- Organization dynamic roles merge without a pre-defined AC instance (D10:
  `organization.go:5598`); role endpoints stay usable in AC-free setups.
  Removal: gate behind an explicit strict flag only.
- `POST /organization/add-member` is kept as an additive HTTP superset (D11:
  upstream documents `addMember` as server-only, `organization.ts:692`).
  No removal policy.
- Organization function-form options (D12:
  `allowUserToCreateOrganization`/`organizationLimit`/`membershipLimit`/
  invitation/team/role limits as functions, `types.ts:32,50,67`) are
  implemented as `*Func` fields alongside the static forms (AUTH-P8-03;
  function-first, fail-closed 500 on func error).
- `POST /verify-email` JSON alias is kept alongside upstream `GET` (D14:
  `email-verification.ts:228`). No removal policy.
- Bounded legacy reads (D15): bcrypt password hashes (`password.go:40`) and
  HMAC email tokens via `VerifyEmailTokenWithFallback` stay readable;
  writers are scrypt/HS256. Removal: drop reads on a major version after an
  expiry window, with a migration note.
- `$brick$` AES-GCM stays the `EncryptString` write format while
  `DecryptString`/`DecryptStringCompatible` also read upstream XChaCha20
  (`$ba$`) payloads (D16: `crypto/index.ts:16-66`). Writer cutover requires
  TS fixtures (Wave 7).
- OIDC request objects (JAR/JARM) are rejected with
  `request_not_supported` (D17), mirroring pinned upstream
  (`authorize.ts:445`, `oauth-endpoint.integration.test.ts:340`); only
  PAR-style `request_uri` resolution is supported. Implementing JAR/JARM is
  explicitly NOT a parity task for v1.7.5. The old backlog row "Implement
  PAR, JAR, JARM" means PAR/`request_uri` only.

### Wave-10 exclusion registry

Narrow, explicit, and tested. Each entry records what is excluded, why, and
the removal policy. Anything not listed here is implemented.

- Dead compat interfaces (W10-01): `TokenEndpointAuth` struct,
  `ClientAssertionProvider`, `TokenAuthMethodProvider`, `DiscoveryProvider`,
  `PrimaryClientID` helper. Zero runtime effect; removal would break in-tree
  consumers and tests asserting them. Preserved as legacy aliases. Removal:
  major-version cleanup with migration notes only.
- Array-form `clientId` (W10-02): Go takes the single primary ID (upstream
  index 0); `Audience`/`IDToken` overrides cover multi-audience verification.
  Removal: widen provider constructors on a major version.
- WeChat dedicated token field (W10-03): the per-instance openid store
  carries openid correctly (fail-closed, refresh supported); a dedicated
  `OAuthTokens` field is cosmetic. Removal: add the field when a second
  consumer needs it.
- `StoreAccountCookie` (W10-04): the Go runtime requires a database adapter,
  so database-less account-cookie flows are out of scope; the option is
  preserved for surface compatibility.
- `AdditionalCookies` (W10-05): no route issues those cookies; the shared-
  domain helper is provided for deployments that do.
- Chunked session-data writes (W10-06): single-cookie writes only; oversize
  caches degrade safely to authoritative lookup (browsers drop oversize
  cookies, producing a cache miss against the store); reads recover
  upstream/custom/chunked names.
- Private-host fetch guards for `jwks_uri`/backchannel URLs (W10-07): not
  implemented; outbound uses a 5s no-redirect client and loopback is allowed
  for hermetic tests.
- `WWW-Authenticate` error headers on OAuth endpoints (W10-08): Huma errors
  carry no headers; statuses are asserted. Removal: Huma header-carrying
  errors or a custom envelope.
- Strict `clientCredentialsScopes` ceiling (W10-09): the legacy fallback is
  kept for compatibility with existing clients; explicit ceilings are
  enforced when set.
- Custom auth-code hashing (W10-10): consume tries the custom hash then the
  default (rotation-safe); issue-side hashing stays default.
- Empty-string `prompt`/`max_age` over GET (W10-11): Huma drops empty query
  values framework-wide; covered via POST.
- `setPassword` HTTP endpoint (W10-12): upstream server-only with no Go HTTP
  owner; password setting flows through create/change/reset routes.
- Extension token-issuance capability surface (W10-13): simplified Go
  envelope signatures, documented in code; full provider capability
  plumbing on token paths stays future work.
- `at_hash` signing-alg heuristic (W10-14): HS256 vs RS256 selection
  documented in code; full `resolveSigningKey` parity open.
- Live MySQL/MSSQL contract runs (W10-15): no MySQL/MSSQL drivers in go.mod
  (intentional, no new dependencies); SQL-generation conformance plus
  SQLite fallback cascades are green.
- Cross-package PostgreSQL parallelism (W10-16): plugin/root harnesses share
  physical tables, so live runs require `-p 1` (documented process); the Bun
  adapter itself is parallel-safe per the isolation matrix.
- Unknown-key additional-field bodies on sign-up (W10-17): Huma structs drop
  unknown keys framework-wide; update paths parse full input.
- Banned social/id-token redirect harnesses (W10-18): no social harness in
  the admin package; the ban hook applies to all session creation (tested).
- Server-call-only shapes (W10-19): Go is HTTP-only; unauthenticated HTTP
  yields 401 in those paths (tested).
- Organization-hook DB org creation via core sign-up (W10-20): covered —
  post-commit hook writes see committed rows and hook failures surface
  their code with the user kept (`hook_signup_test.go`).
- Client-only test areas (W10-21): `useSession` revalidation,
  `checkRolePermission`, client declaration files — no Go client exists.

Go compiles packages on demand, so plugins stay in separate packages but in
the same module. Applications that do not import `plugins/jwt`, for example,
do not include it in their binaries.

## Upgrade and conformance process

1. Update `vendor/better-auth` to a stable upstream tag.
2. Update `BetterAuthVersion` in `version.go`.
3. Diff every mapped source area and regenerate the endpoint/provider lists.
4. Port behavior together with the corresponding upstream tests; do not mark a
   route complete because its happy path or name matches.
5. Preserve existing Go compatibility where possible and document migrations
   where upstream-compatible wire/storage formats require a breaking change.
6. Run `GOWORK=off go build ./...`, `go vet ./...`, `go test -race ./...`, and
   `go test -coverpkg=./... ./...` from `auth/`. Live-PostgreSQL runs
   are green serially (`DATABASE_URL=... GOWORK=off go test -p 1
   -count=1 ./...`); cross-package parallel runs share one database and
   interfere, so keep `-p 1` until per-test schema isolation lands.
